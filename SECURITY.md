# Security policy

urMQTT is alpha (since v0.4.2). No release is fit for unattended production yet; see [docs/KNOWN-ISSUES.md](docs/KNOWN-ISSUES.md).

## Reporting a vulnerability

Please **do not open a public issue**. Report it privately through
[GitHub Security Advisories](https://github.com/zeljan-alduk/urMQTT/security/advisories/new).
Include the affected commit, a reproducer (a fuzz input is ideal) and the impact
you expect.

You can expect an acknowledgement within 7 days. The whole process (triage, fix
targets, disclosure, supported versions) is in
[docs/VULNERABILITY-HANDLING.md](docs/VULNERABILITY-HANDLING.md). Fixes are released as a new
image, because urMQTT has no in-place update mechanism by design.

## Scope

The parsers (MQTT, TLS records, TCP/IP, configuration, DTB/ACPI, the WebSocket
upgrade and frames) and anything reachable from TCP 8883, or from the optional
plaintext (`[plaintext]`) and secure WebSocket (`[websocket]`, `wss://`, default
port 8084) listeners when an image turns them on, are in scope. The threat model lives in
[docs/SECURITY.md](docs/SECURITY.md).

Dev certificates generated by `scripts/gen-dev-certs.sh`, and the dev images
attached to GitHub releases up to v0.4.1, embed throwaway keys and are **not**
secrets. Reports about them are out of scope.

## Release signing keys

Releases are signed with [minisign](https://jedisct1.github.io/minisign/): `SHA256SUMS.minisig` over `SHA256SUMS`.
Compare the key id the builder page shows, and the key you verify with, with this table.

| Key | Id | Public key | Trusted for |
|---|---|---|---|
| release key, [`minisign.pub`](minisign.pub) | `721316B961DCB94B` (set at the rotation, docs/release-key-rotation.md) | `RWRLudxhuRYTcpqyk9TNXAj1qzClrFEvzXTyFMBK6NEuyvk6tVUxjUlH` | every release after v0.4.1 |
| former test key, [`keys/minisign-test-9229E05252D01F8E.pub`](keys/minisign-test-9229E05252D01F8E.pub) | `9229E05252D01F8E` | `RWSOH9BSUuApkkBWq/AZJ03Rn63oOYq+yXzC/vgI1PZ/i5yaE+SVzOWS` | **v0.1.0 to v0.4.1 only** |

**The former test key is considered compromised** from the day the release key exists: its secret half was a
passwordless CI secret and a file on a developer machine. Its signatures on v0.1.0 to v0.4.1 stay valid; a signature
by it on any later tag is a forgery, and the builder page, the release mirror and `scripts/check-release-key.sh` refuse
it. For the tags it did sign, only the published `SHA256SUMS` is accepted: the key ring pins the SHA-256 of each
(`pinned` in `keys/release-keys.json`), so a file the leaked key signs for an old tag is refused too. Report such a file as a vulnerability (docs/VULNERABILITY-HANDLING.md). The key ring with the ranges is
[`keys/release-keys.json`](keys/release-keys.json).
