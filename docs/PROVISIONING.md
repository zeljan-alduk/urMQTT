# Provisioning, trust anchors and the identity lifecycle

> Status: H1. The broker side is implemented and tested (ADR-048, ADR-049).
> The enrollment service is outside urMQTT by design; this document says what
> it must do.

## Principles

- **Device keys are born on the device** and never leave it, ideally inside a
  secure element (ATECC608, SE050, a TPM, or the SoC's key store). Nobody keeps
  a central store of device private keys.
- **Certificate authorities live in an HSM or cloud KMS.** The broker image holds
  only CA *certificates* (trust anchors), its own server key, and the *public*
  control key.
- **Two roles of trust anchor** (`[trust]` in `deploy/<env>/config.toml`):
  - `operational` CAs issue device and service certificates. Their holders get
    the ACL's device or service rights.
  - `bootstrap` CAs issue factory certificates. A bootstrap identity may use
    `provision/{id}/#` and nothing else. Its session is always clean, and it
    lives in its own namespace, so it can neither take over nor read the
    operational session of the same id.
- **Every change of who may connect is authenticated twice.** It needs an mTLS
  control identity *and* an offline Ed25519 signature (control channel,
  docs/SECURITY.md).

## The flow

```text
 factory                      field                                  backend (outside the broker)
 ───────                      ─────                                  ────────────────────────────
 device generates key pair    device connects with the bootstrap
 in its secure element        certificate (CN = device id)
         │                                │
 bootstrap CA (HSM) signs     publishes a CSR to                     enrollment service, subscribed
 a factory certificate        provision/<id>/csr  ─────────────────▶ as a service to provision/+/csr:
 (role: bootstrap)                                                    checks the CSR against the
                                                                      factory record, has the
                              receives its operational               operational CA (HSM/KMS) sign it
                              certificate on        ◀─────────────── and publishes it to
                              provision/<id>/cert                     provision/<id>/cert
                                          │
                              reconnects with the operational
                              certificate: device rights
                                          │                          (allowlist mode only)
                                          │                          the operator signs and sends
                                          │                          `urmqtt-control allow --id <id>`
```

For the enrollment service to work, the image must give it service rights on the
provisioning tree:
- `acl.service_ids` lists it;
- `acl.service_subscribe` contains `provision/+/csr`;
- `acl.service_publish` contains `provision/+/cert`.

The bootstrap identity's own rights are fixed (`provision/{id}/#`), whatever the
ACL says.

## Generating the material

Development material is generated by `make certs` (`scripts/gen-dev-certs.sh`):
two operational CAs (`ca.pem`, `ca-2.pem`), a bootstrap CA, a device of each
CA, a bootstrap identity (`bootstrap/device-006`), the control service identity
`operator` and the control key pair. In production:

| Material | Where it is made | Where it goes |
|---|---|---|
| Operational CA key | HSM / KMS | never leaves it; `ca*.pem` into `deploy/prod/` |
| Bootstrap CA key | HSM at the factory | never leaves it; its certificate into `deploy/prod/` |
| Server key | the build operator's machine or a KMS export | `deploy/prod/server.key` (the image is then secret, docs/SECURITY.md) |
| Control signing key | HSM / KMS (`--sign-cmd`), or an offline machine | **never in the image**; `control.pub` into `deploy/prod/` |
| Device keys | the device | never leave it |

Control key, offline machine variant (OpenSSL ≥ 3):

```sh
openssl genpkey -algorithm ed25519 -out control.key   # keep offline
openssl pkey -in control.key -pubout -out deploy/prod/control.pub
```

The build rejects anything that is not an Ed25519 `BEGIN PUBLIC KEY`.

## CA rotation with overlap

1. Create the new operational CA. Add its file to `trust.operational` next to the
   old one and deploy the image. Both CAs are now accepted.
2. Re-issue device certificates under the new CA, through the provisioning flow
   or the device's own renewal.
3. When no device uses the old CA, remove it from `trust.operational` and
   deploy. Its certificates are refused at the next full handshake **and at the
   next resumption**: a resumed session re-verifies its chain against the
   current anchors.

The build fails if any anchor expires within `trust.min_anchor_days` (365), or the
server certificate within `tls.min_server_cert_days` (60), counted from the build
time. At runtime the broker exports the remaining days as the statsd gauge
`urmqtt.tls.server_cert_days` and logs a warning at 60, 30, 7 and 1 days left.

## Revocation and the allowlist at runtime

`tools/urmqtt-control` builds, signs and publishes control messages:

```sh
# revoke a device (by its certificate, or --serial HEX)
urmqtt-control revoke --cert device.pem --env prod --sign-cmd "$SIGNER" \
    --host broker.example --ca ca.pem --client-cert operator.pem --client-key operator.key

# allowlist mode (registry.mode = "allowlist")
urmqtt-control allow --id device-042 ...
urmqtt-control disallow --id device-042 ...
```

What happens on the broker:
- A message is applied only after it is committed to the data disk, together
  with its sequence number.
- Live connections of a newly revoked certificate, or of an identity that left
  the allowlist, are closed at once. In the smoke tests that takes 3–10 ms
  after the commit.
- A rejected message (bad signature, replayed `seq`, outside its window, wrong
  mode, no durable storage) is counted under `urmqtt.control.rejected.<reason>`
  and logged with its reason only.

**Signing hook.** `--sign-cmd 'CMD'` runs `CMD` with the bytes to sign on stdin.
It expects the 64-byte Ed25519 signature on stdout, raw or as hex. With
OpenSSL 3 and a key file:
`f=$(mktemp); cat >"$f"; openssl pkeyutl -sign -inkey control.key -rawin -in "$f"; rm "$f"`.
For an HSM use `pkcs11-tool --sign --mechanism EDDSA`. For a cloud KMS, use its
CLI with the raw-message Ed25519 mode. urMQTT has no PKCS#11 library linked in
itself; every hardware key goes through this hook.

**Sequence numbers** default to the current Unix time in milliseconds, so two
operators need no shared counter, as long as their clocks are sane. A message
with a `seq` at or below the last applied one is a replay.

**Allowlist exemptions.** Identities in `acl.service_ids` and
`control.service_ids` are named in the image and are not subject to the
allowlist. Bootstrap identities are not subject to it either, because
provisioning is how a device becomes known.
